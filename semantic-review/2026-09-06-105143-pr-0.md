# PostgreSQL concurrency-token and scheduler race hardening

The change remaps `Repository` and `AnalysisJob` concurrency tokens to PostgreSQL `xmin`, canonicalizes campaign occurrence timestamps to PostgreSQL precision, reconciles duplicate dispatch failures, and replaces timing-dependent race tests with a `SaveChangesInterceptor` gate. The `uint`/`IsRowVersion()` mapping and microsecond quantization match the intended Npgsql behavior, while the gate forces both schedulers to stage the same occurrence and version before either write starts. The blockers are failure isolation in the new `DbUpdateException` path and migration/rollback safety; the PostgreSQL fixture also bypasses the migration it should validate. **Watch for:** **confirmed** failed dispatch entries can be replayed into later campaigns; **confirmed** any database-update failure can be reclassified from job existence alone; **likely** the `xmin` cutover breaks mixed-version rollout; **confirmed** `Down` restores non-rotating tokens; **likely** a database-name prefix is too broad for an unconditional drop; and **confirmed** migration/provider proof is incomplete.

**Verdict**: NEEDS_CHANGES

## High-level view

The scheduler treats either an optimistic-concurrency exception or a database-update exception followed by a matching occurrence as a lost claim. The rethrow path leaves the failed campaign’s job, audit, and mutation pending, and the existence check does not establish which constraint failed or whether the cursor and dispatch audit committed; both gaps are **confirmed** in the new branch.

`Repository.RowVersion` and `AnalysisJob.RowVersion` correctly model Npgsql’s `xmin` token. The one-step column drop is **likely** incompatible with an older instance still using the `byte[]` model, while rollback **confirmedly** recreates one identical empty token for every row without any update-time rotation.

Microsecond occurrence-key normalization preserves keys produced from persisted PostgreSQL timestamps. The provider test **confirmedly** does not force a sub-microsecond input, so it can pass without detecting the original precision mismatch.

The save gate ensures both contexts reach `SavingChangesAsync` with version `1` and the same occurrence. The fixture **confirmedly** uses `EnsureCreatedAsync`, so it does not execute the migration, prove `xmin` stale-writer rejection, or distinguish the new reconciliation branches.

The external fixture requires a test-prefixed database, but the **likely** residual data-safety risk is that this prefix is the only check before deleting a caller-selected database on any host at setup and teardown.

1. **Failed dispatch state replay (High, confirmed)** — an unrelated `DbUpdateException` is rethrown without clearing the failed job, audit, and campaign mutation, so later campaigns can retry or commit them. Detach that state before continuing, or isolate each dispatch in its own context.
2. **Over-broad claim-lost classification (High, confirmed)** — any `DbUpdateException` becomes `SkippedClaimLost` when a matching job exists, without checking the expected constraint or complete atomic state. Validate SQLSTATE/constraint and reconcile the job, campaign version/cursor, and audit before suppressing an error.
3. **Mixed-version `xmin` cutover (Medium, likely)** — startup migration drops columns still required by older binaries. Use an expand/contract migration or require and document a fully drained deployment.
4. **Non-rotating rollback tokens (Medium, confirmed)** — `Down` gives every row the same empty `bytea` value and never changes it on updates. Restore a generated token or mark the migration irreversible.
5. **Prefix-only destructive database guard (Medium, likely)** — any caller-selected database beginning `apihunter_race_` is deleted on any host. Require a second destructive opt-in and a run-specific target, or let the fixture create its own uniquely named database.
6. **Migration and reconciliation proof gap (Medium, confirmed)** — the hard gate creates the latest model and does not test migration `Up/Down`, `xmin` stale writers, the expected unique-constraint branch, or unrelated database failures. Add migration-based PostgreSQL tests that force each path.
7. **Vacuous provider precision check (Low, confirmed)** — the round-trip test does not guarantee non-microsecond ticks. Seed a fixed timestamp with a known tick remainder and assert raw precision changes while the key remains stable.

<details><summary>Details</summary>

## Failed database writes remain queued for the next campaign

**High — confirmed.** When `SaveChangesAsync` throws a `DbUpdateException` and no matching occurrence is found, the branch rethrows without detaching the added scan job and audit or the modified campaign (`src/Platform.Application/Services/CampaignDispatchService.cs:619-633`). `RunSchedulerTickAsync` catches it and continues over due campaigns with the same context (`CampaignDispatchService.cs:107-132`). The next save therefore includes the first campaign’s failed changes: a permanent constraint failure can poison the remaining tick, while a transient failure can commit an earlier dispatch during a later campaign and corrupt per-campaign results.

Clear the failed entries before rethrowing, or use a fresh context per campaign. A multi-campaign test should force an unrelated constraint failure first and prove the second dispatch neither retries nor persists the first campaign’s state.

## Occurrence existence does not identify the failed database operation

**High — confirmed.** The catch covers every `DbUpdateException`, then reports `SkippedClaimLost` whenever any row has the same campaign and occurrence key (`CampaignDispatchService.cs:619-649`). It checks neither PostgreSQL SQLSTATE/constraint name nor the rest of the claimed atomic state—an advanced campaign version/cursor and matching dispatch audit. A matching job can therefore hide an unrelated integrity failure or partial/non-scheduler insertion.

Classify the expected unique violation using `PostgresException.SqlState` and `ConstraintName == "IX_security_scan_jobs_campaign_occurrence_key"`. For ambiguous commit acknowledgements, verify the job identity, campaign occurrence/version, and dispatch audit before suppressing any other exception. The gated tests assert only the final winner/loser result (`tests/Platform.IntegrationTests/Scanning/CampaignSchedulerRaceTests.cs:243-278`), not which branch ran or whether unrelated errors escape.

## `xmin` cutover is not safe for mixed application versions

**Medium — likely.** The migration immediately drops both `RowVersion` columns (`src/Platform.Infrastructure/Persistence/Migrations/20260906024820_FixPostgreSqlRowVersionTokens.cs:12-23`), while the new model maps those properties to `xmin` (`src/Platform.Infrastructure/Persistence/PlatformDbContext.cs:207-218,333-344`). Because the API applies migrations at startup (`src/Platform.Api/Program.cs:503-507`), the first new instance can remove columns while older instances still select and update them as `byte[]`.

Use an expand/contract rollout that keeps the old columns writable until old instances drain, then drop them later. If deployment is stop-the-world, make that an explicit release requirement.

## Migration rollback silently disables optimistic concurrency

**Medium — confirmed.** `Down` recreates each column as `NOT NULL DEFAULT '\x'` (`FixPostgreSqlRowVersionTokens.cs:27-43`). The default applies only on insert; no trigger changes it on update, so restored rows share an empty token and stale writers continue to match.

Make the migration explicitly irreversible, or restore a database-generated token that changes on every update and test stale-writer rejection against the downgraded model.

## Prefix-only validation still permits destructive external targets

**Medium — likely.** A connection is accepted solely when `Database` starts with `apihunter_race_` (`tests/Platform.IntegrationTests/Scanning/CampaignSchedulerRaceTests.cs:60-75`), then setup and teardown delete the entire database (`CampaignSchedulerRaceTests.cs:102-104,136-141`). This permits any host and names such as `apihunter_race_shared`; the fixture cannot establish disposability.

Require a separate destructive-test opt-in and run-specific identifier, or have the fixture create and drop a uniquely generated child database. Keep the current fail-closed behavior when neither Docker nor an approved target is available.

## The hard gate does not exercise migrations or both reconciliation branches

**Medium — confirmed.** The fixture calls `EnsureCreatedAsync` (`CampaignSchedulerRaceTests.cs:102-104`), bypassing `FixPostgreSqlRowVersionTokens.Up` and migration history. No PostgreSQL test starts from the prior `bytea` schema, migrates forward, inserts and concurrently updates both entity types, or migrates down. No test forces the expected-constraint `DbUpdateException` and an unrelated `DbUpdateException`, so classification and cleanup remain unproved despite the deterministic contention gate (`CampaignSchedulerRaceTests.cs:503-594`).

## Provider precision test can pass without losing precision

**Low — confirmed.** The unit test deliberately compares timestamps seven ticks apart (`tests/Platform.UnitTests/Scanning/CampaignDispatchServiceTests.cs:146-160`). The PostgreSQL test instead seeds from `DateTime.UtcNow` (`tests/Platform.IntegrationTests/Scanning/CampaignSchedulerRaceTests.cs:190-202`) and compares only pre-save and reloaded keys (`CampaignSchedulerRaceTests.cs:290-309`). If the clock value is already microsecond-aligned, the old implementation also passes.

Seed a fixed UTC timestamp with a non-zero tick remainder, assert the reloaded raw ticks differ, then assert the keys match.

### Validation

The focused `CampaignDispatchServiceTests` suite passed 23/23, and the affected projects built. Generated migration SQL contains the expected forward drops and reverse static-empty-`bytea` additions. The five PostgreSQL race tests could not run because neither `TEST_POSTGRES_CONNECTION_STRING` nor Docker was available; all failed during fixture initialization.
