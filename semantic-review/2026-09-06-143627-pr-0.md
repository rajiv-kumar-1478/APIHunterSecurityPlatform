# Tenant-owned scanner execution and PostgreSQL scheduler hardening

This change moves browser access to cookie-only, database-revalidated sessions; adds tenant-owned scan-job consumption and heartbeat fencing; hardens campaign dispatch reconciliation; and reconciles PostgreSQL migration history and concurrency tokens. The prior findings around failed `DbUpdateException` replay, over-broad duplicate classification, destructive fixture targeting, native `xmin`, irreversible rollback, and sub-microsecond occurrence identity are materially addressed. Two failure/rollout gaps remain. **Watch for:** **likely blocker** — a direct Npgsql COMMIT transport failure bypasses cleanup and reconciliation; **confirmed blocker** — required `TenantId` plus nullable requester rows break old scan-job writers/readers during the claimed mixed-binary window; **confirmed non-blocking gap** — documentation marks both token bridges as provider-proven although the PostgreSQL suite never exercises `Version`/`JobVersion` interoperability.

**Verdict**: NEEDS_CHANGES

## High-level view

The API now applies fallback authentication, durable session revalidation, and global unsafe-method antiforgery enforcement; the frontend centralizes cookie/CSRF requests without browser-stored bearer credentials. The private worker claims tenant-owned jobs with conditional updates and heartbeat-fenced terminal writes, while disabled scanner mode remains fail closed.

Campaign dispatch detaches failed tracked writes and suppresses only an exact PostgreSQL occurrence-key violation or a classified ambiguous outcome after verifying the complete job/campaign/audit tuple. The remaining boundary accepts only `DbUpdateException`, so the transport failure most specific to an uncertain COMMIT can escape as a provider exception.

`Repository` and `AnalysisJob` use native `xmin` while generated legacy `bytea` columns preserve old-token updates. `security_scan_jobs.Version` and `JobVersion` are synchronized in both directions, but the preceding tenant/requester migration prevents unrestricted old/new scan-job binaries from coexisting, so the counter bridge alone does not make that rollout safe.

The guarded PostgreSQL fixture applies migrations, proves stale `xmin`, rotates legacy row versions, and uses a non-vacuous seven-tick timestamp. It does not simulate a lost COMMIT acknowledgement or access the legacy scan-job `Version` column, despite documentation presenting both behaviors as accepted provider evidence.

## COMMIT acknowledgement failures bypass dispatch cleanup

**High — blocker — likely.** `AtomicDispatchAsync` clears failed entries and reconciles durable state only in its `DbUpdateConcurrencyException` and `DbUpdateException` catches (`src/Platform.Application/Services/CampaignDispatchService.cs:634-704`); the provider-neutral classifier also accepts only `DbUpdateException` for ambiguous outcomes (`src/Platform.Application/Persistence/IDatabaseErrorClassifier.cs:15-22`). A connection failure while EF commits its relational transaction can propagate the provider exception directly, at the point where the server may have committed without returning acknowledgement.

That exception reaches the tick-level `catch (Exception)` (`CampaignDispatchService.cs:133-138`) without `DiscardPendingChanges()` or tuple reconciliation. The shared context can therefore carry the staged job/audit/campaign state into the next due campaign. The ambiguous-failure test does not exercise this seam: it manually saves one job, inserts the same key again, and asserts the unique violation (`tests/Platform.IntegrationTests/Scanning/CampaignSchedulerRaceTests.cs:349-438`).

Broaden ambiguous classification to the actual exception surface, preserve cancellation handling, and detach pending entries after every failed atomic save. A transaction interceptor or connection-fault test should prove both post-COMMIT reconciliation and clean pre-COMMIT rethrow behavior.

## Scan-job ownership changes break the mixed-binary rollout contract

**Medium — blocker — confirmed.** The ownership migration makes `RequestedByUserId` nullable (`src/Platform.Infrastructure/Persistence/Migrations/20260905205518_AddScanJobTenantOwnership.cs:57-64`), adds `TenantId` without an insert bridge, then makes it required (`AddScanJobTenantOwnership.cs:104-165`). New campaign jobs persist the tenant and a null requester (`src/Platform.Application/Services/CampaignDispatchService.cs:575-576`), matching the new entity contract (`src/Platform.Domain/Entities/SecurityScanJob.cs:23-29`).

The pre-change binary has no `TenantId` property and models `RequestedByUserId` as non-nullable. After migration, an old writer omits required ownership and an old reader cannot materialize a new scheduler row with a null requester. The later counter trigger does synchronize updates (`src/Platform.Infrastructure/Persistence/Migrations/20260906024820_FixPostgreSqlRowVersionTokens.cs:105-154`), but it cannot make the rest of the row contract compatible. This contradicts the mixed-binary language in `README.md:128-129` and `docs/MASTER_BLUEPRINT.md:2443-2446`.

Use an ownership/requester expand-contract sequence, or require all old scan-job API/scheduler/worker binaries to drain before migration and narrow the rolling-safety claims accordingly.

## The scan-job version bridge is asserted in docs, not in the provider suite

**Low — non-blocking — confirmed.** The real-provider suite verifies the corrective migration, stale `xmin`, and rotating legacy `Repository`/`AnalysisJob` tokens (`tests/Platform.IntegrationTests/Scanning/CampaignSchedulerRaceTests.cs:604-702`). Its only scan-job counter mutation changes `JobVersion` (`CampaignSchedulerRaceTests.cs:492-495`); no test accesses legacy `Version`. README nevertheless says the seven tests cover “migration bridges” (`README.md:135-156`), and the acceptance matrix marks synchronized counters green (`docs/MASTER_BLUEPRINT.md:2451-2466`).

Add raw-SQL legacy-writer tests for bidirectional propagation and stale-writer rejection, or describe the trigger as code-reviewed rather than provider-tested.
