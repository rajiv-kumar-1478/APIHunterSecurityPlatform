# Direct provider-failure boundary and narrowed scan-job rollout claims

This pass re-reviews the same uncommitted worktree after the two blocking findings were addressed. `AtomicDispatchAsync` now separates concurrency, cancellation, and every other failure: it always detaches the failed atomic batch, classifies a unique violation only from a `DbUpdateException`, classifies an ambiguous commit from any exception through `IDatabaseErrorClassifier.IsPotentiallyAmbiguousCommitFailure(Exception)`, rethrows immediately when neither applies, and otherwise reconciles the complete durable job/campaign/audit tuple. The mixed-binary rollout overclaim was resolved by narrowing language rather than patching schema: `AddScanJobTenantOwnership` is stated as a mandatory stop/drain boundary and every bridge claim is scoped to tenant-schema-compatible clients. Two new PostgreSQL facts cover pre-commit rollback plus post-commit acknowledgement loss, and bidirectional `Version`/`JobVersion` fencing. **Watch for:** **confirmed non-blocking** — a durable dispatch that loses its acknowledgement is counted and audited as `SkippedClaimLost`, so dispatch metrics undercount; **confirmed non-blocking** — the classifier's two methods take different parameter types, and neither classification runs when the classifier is not registered, with no unit test or DI assertion guarding it; **likely non-blocking** — the post-commit test throws after EF accepted changes, so it never exercises a dirty tracker together with committed durable state.

**Verdict**: APPROVED

## High-level view

The direct-provider gap is closed. Cancellation is separated from failure classification before the general catch, `DiscardPendingChanges()` runs on every failure path, and reconciliation still demands the full committed tuple, so broadening ambiguity classification to bare provider exceptions cannot suppress an error on a partial row. Shutdown does not regress into error counting or a host stop: the tick rethrows `OperationCanceledException` only for its own token, and `CampaignSchedulerWorker` breaks its loops on it.

The PostgreSQL classifier treats any `PostgresException` in the chain as a definitive server answer and only a transient `NpgsqlException` as an unknown commit outcome. The interface is now half-typed, though: unique-violation classification still requires `DbUpdateException`, and the classifier is an optional constructor dependency registered in exactly one host, so its absence degrades silently to "rethrow everything" with no test noticing.

Reconciliation after acknowledgement loss reports the caller's own successful dispatch as a claim loss. Safety holds — one job, one `Dispatched` audit — but the tick counts `ClaimLost` instead of `Dispatched` and writes a second audit row for the same occurrence, which the new test pins as expected behavior.

The rollout claim is consistent everywhere: no document, migration comment, or `Down` message in the tree still asserts mixed-binary or rolling safety, and the boundary appears in README, implementation status, memory, decisions, blueprint, and worker operations. The migration that *is* the boundary carries no in-code note of it — the drain requirement lives only in prose.

The `Version`/`JobVersion` evidence gap is closed by a real-provider test covering insert-time merge, propagation in both directions, and stale-writer rejection from both writers. What neither new test covers is a genuine transport break: both failures are injected by a `SaveChangesInterceptor`, so classifier wiring is proven while broken-connection behavior of the follow-up reconciliation queries is not.

## Direct provider failures now reach cleanup and reconciliation

The catch chain in `AtomicDispatchAsync` (`src/Platform.Application/Services/CampaignDispatchService.cs:638-720`) orders concurrency, cancellation, then everything else; EF does not wrap `OperationCanceledException` in `DbUpdateException`, so the cancellation catch is reachable and the general catch cannot mistake a shutdown for a provider fault. Broadening ambiguity to bare exceptions is conservative rather than permissive: a transient `NpgsqlException` wrapped in `DbUpdateException` from a failed modification command is also classified ambiguous, but with nothing committed the tuple lookup returns null and the exception rethrows — what the pre-commit half of the new test asserts (`tests/Platform.IntegrationTests/Scanning/CampaignSchedulerRaceTests.cs:812-840`: `Errors=1`, no job, no audit, and the next campaign in the same tick saving cleanly).

The rough edge is the outcome label. On acknowledgement loss the committed tuple is the caller's own write, yet the path returns `SkippedClaimLost` with the reason "A complete competing atomic dispatch was verified after an ambiguous commit acknowledgement failure" (`CampaignDispatchService.cs:711-719`), and the new test pins `Dispatched=0`, `ClaimLost=1`, plus one `Dispatched` and one `SkippedClaimLost` audit for the same occurrence (`CampaignSchedulerRaceTests.cs:846-873`). Nothing duplicates, but a diagnostic reader sees a claim loss where the scheduler in fact succeeded, and that audit row records `ScheduleVersion` as the pre-dispatch expectation while the campaign durably advanced past it.

Cancellation carries its own asymmetry. An `OperationCanceledException` raised while the scheduler token is *not* cancelled — a provider-internal cancellation — skips the tick's rethrow guard (`CampaignDispatchService.cs:133-140`) and is counted as an error, after the batch was already detached. In both cancellation shapes, a commit that landed is never reconciled: durable safety comes from the advanced cursor and the occurrence-key unique index on the next tick, not from an audit trail.

## Classifier rules are coherent; its contract and wiring are not

`IsPotentiallyAmbiguousCommitFailure` walks the chain twice: any `PostgresException` returns false first, then a transient `NpgsqlException` returns true (`src/Platform.Infrastructure/Persistence/PostgreSqlDatabaseErrorClassifier.cs:32-56`). Definitive-first ordering matters here, because `PostgresException.IsTransient` is true for several SQLSTATEs that are still definitive server answers; short-circuiting on the type keeps a serialization failure from being read as an unknown commit.

The interface is mixed: `IsUniqueConstraintViolation(DbUpdateException, string)` against `IsPotentiallyAmbiguousCommitFailure(Exception)` (`src/Platform.Application/Persistence/IDatabaseErrorClassifier.cs:12-23`). A unique violation surfaced outside EF's wrapper — a deferred constraint raised at commit, for instance — is classified as neither, because the cast fails and the `PostgresException` forces ambiguity to false, so the dispatch rethrows without reconciliation. The occurrence-key index is a plain partial unique index, so today's exposure is small, but the asymmetry invites decay.

Wiring is the sharper issue. `_databaseErrorClassifier` is optional and consulted with `?.` (`CampaignDispatchService.cs:69-86,676-683`), and the only registration in the tree is `AddSingleton<IDatabaseErrorClassifier, PostgreSqlDatabaseErrorClassifier>()` in `src/Platform.Worker/Program.cs:172`. The API neither registers nor resolves `ICampaignDispatchService`, so no live host diverges today. But no test references the interface or the implementation: unit tests build the dispatch service without a classifier, and the rules are exercised only by the PostgreSQL-gated suite. Deleting that one registration keeps 747 unit and 106 integration tests green while ambiguous-commit reconciliation and duplicate-occurrence suppression both stop working. The failure mode is fail-closed — errors counted rather than wrongly suppressed — which is why this is not blocking, and the classifier is a pure class that unit tests can construct directly.

## Provider-failure injection proves the wiring, not the transport

Both halves of `DirectProviderFailures_PreCommitRollbackAndPostCommitAcknowledgementLossRemainSafe` inject an `NpgsqlException` with an `IOException` inner from a `SaveChangesInterceptor` (`CampaignSchedulerRaceTests.cs:875-940`), gated on the dispatch batch shape and latched to fire once.

The post-commit half throws from `SavedChangesAsync`, which EF invokes after the state manager accepted the changes, so every entry is `Unchanged` by the time `DiscardPendingChanges()` runs and the "no Added/Modified/Deleted entries" assertion on that path holds trivially; detachment is proven only by the pre-commit half. A real connection break during `COMMIT` produces both conditions at once — dirty tracked state and a committed tuple — and leaves the pooled connection broken, so the reconciliation queries that follow run on a connection EF must re-establish. Injecting at `TransactionCommittingAsync`, or terminating the backend with `pg_terminate_backend`, would cover both.

## Version bridge evidence now matches the claim

`SecurityScanJobVersionBridge_LegacyAndCurrentWritesSynchronizeBidirectionally` (`CampaignSchedulerRaceTests.cs:743-796`) reads and writes the physical legacy column over raw Npgsql: insert merges both counters to `(3, 3)`; a conditional legacy write to `7` advances `JobVersion` and invalidates an already-loaded current writer with `DbUpdateConcurrencyException`; a current EF write to `11` advances the legacy column; and a stale conditional legacy update affects zero rows. That covers all four documented claims, closing the previous documented-but-unproved gap.

## Rollout narrowing is consistent, except inside the boundary migration

No schema patch was attempted, which is the safer call given the required `TenantId` plus nullable requester contract. Claims now match: README describes a deployment stop/drain boundary and scopes the counter bridge to tenant-schema-compatible clients (`README.md:128-130`), with the same framing in `docs/IMPLEMENTATION_STATUS.md:28`, `docs/AI_PROJECT_MEMORY.md:39`, `docs/DECISIONS.md:287,300-301`, `docs/MASTER_BLUEPRINT.md:2390,2443-2447`, and `docs/operations/scanner-worker.md:24`. A tree-wide search for `mixed-binary`, `rolling`, and `zero-downtime` across documents and migrations returns nothing, so no residual overclaim survives. `FixPostgreSqlRowVersionTokens` carries the narrowed comments and the `0A000` refusal naming both the drain precondition and the required contract migration (`20260906024820_FixPostgreSqlRowVersionTokens.cs:13-19,117-121,177-182`).

`20260905205518_AddScanJobTenantOwnership` itself says nothing about being that boundary. Its summary covers tenant ownership and requester optionality (`:8-11`), its comments explain backfill and abort semantics, and its `Down` refuses only when null requesters exist (`:308-326`). An operator reading the migration before `dotnet ef database update` gets no signal that pre-tenant binaries must stop first.
